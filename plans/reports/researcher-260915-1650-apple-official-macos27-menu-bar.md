# Official Apple Sources on macOS 27 "Golden Gate" and the Menu Bar

Date: 2026-09-15. Scope: official Apple sources only (developer.apple.com DocC JSON, WWDC26 session transcripts, support.apple.com). No repo files changed. This report complements, and in one place corrects the scope of, the same-day `researcher-260915-1340-macos27-menu-bar-hiding-techniques.md` report, which explicitly could not get past developer.apple.com's JS gate and relied on third-party source archaeology instead.

## Outcome

Apple's official macOS 27 Release Notes, NSStatusItem/NSMenuItem API reference, and the WWDC26 "Modernize your AppKit app" session together document exactly one new public API relevant to menu bar work: `NSStatusItem.expandedInterfaceDelegate` / `NSStatusItemExpandedInterfaceSession`, a mechanism for a status item to present a custom window (instead of an `NSMenu`) when clicked, with AppKit tracking its keyboard-focus lifecycle. This is new in macOS 27.0 and is scoped to an app's *own* status item — it is not a public replacement for reading, moving, or hiding *other* apps' status items, so it does not change the conclusion of the prior report that no public API exists for third-party menu bar management. Apple's official documentation is otherwise silent on every mechanism the prior report reverse-engineered: nothing about `MenuBarAgent`, the single-composited-window WindowServer change, the overflow chevron's layout algorithm, or any CGWindowList/SkyLight change. `CGWindowListCreateImage` and `CGWindowListCopyWindowInfo` carry no deprecation flag in the live docs today (`deprecated: false`), and ScreenCaptureKit is not mentioned anywhere in the macOS 27 release notes. Two privacy/security changes are documented and relevant to Skein's non-sandboxed, Personal-Team-signed distribution: apps can no longer read the local TCC database directly (a new, unqualified deprecation), and cross-developer-team app-data/app-group container access is now denied by default with no user prompt (previously prompted), manageable only in Privacy & Security Settings. The user-facing "Allow in the Menu Bar" per-app toggle is confirmed by an official Apple support guide, but that guide's version selector tops out at "macOS Tahoe 26" with no macOS 27 edition yet published (macOS 27 GA'd 2026-09-14, one day before this research) — the content I found is inherited, not confirmed current for 27.

## 1. Menu bar / status item / CGWindowList / accessibility of menu extras

**Apple documents a menu-item image-visibility reversal (AppKit, not NSStatusItem):** the macOS 27 Release Notes AppKit section states: *"In macOS 27.0, menu bar and context menus present a reduced set of menu item images, similar to the behavior prior to macOS 26.0. By default, `NSMenu` hides all menu item symbol images — non-symbol images remain visible... These changes in menu item image visibility apply to applications linked on macOS 26.0 and later... Use the new `preferredImageVisibility` property on `NSMenuItem` to customize the image visibility for your menu items."* (ID 170477566) A Resolved Issues entry sharpens this further: *"For applications linked on the macOS 27 SDK, both symbol and non-symbol menu item images are now automatically hidden."* (179374305) — Source: https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes

**Apple documents keyboard accessibility of status items explicitly, in WWDC26 session 289 "Modernize your AppKit app":** *"Keyboard navigation also reaches beyond your app's windows, into the menu bar and status items. Navigating across status items is a little different from main menu items. Status items that show a menu when clicked, already behave like menus on the menu bar. But status items can also be triggers, for actions or display some kind of transient UI... To trigger an action, modify NSStatusItem's button property to include a target and action, and optionally an image. This behaves like a regular button and the action fires automatically when Return is pressed during keyboard navigation."* — Source: https://developer.apple.com/videos/play/wwdc2026/289/

**Apple documents (unchanged, not new in 27) that a status item can be pushed into the system's own overflow:** the `isVisible` reference page states: *"This property returns [true] even if the status item is temporarily hidden due to insufficient space in the menu bar."* (introducedAt macOS 10.12, i.e. long-standing, not a macOS 27 change) — Source: https://developer.apple.com/documentation/appkit/nsstatusitem/isvisible

**Apple documents nothing about `MenuBarAgent`, `CGSGetProcessMenuBarWindowList`, SkyLight, the single-composited-window WindowServer change, or the overflow chevron's layout algorithm.** I grepped the full macOS 27 Release Notes JSON (all ~310 heading/list items across every subsystem) for `StatusItem`, `StatusBar`, `ScreenCaptureKit`, `CGWindowList`, `SkyLight`, `Control Center`, `ControlWidget`, and `MenuBarExtra`: zero hits for all of them except three occurrences of the literal phrase "menu bar," all inside the single AppKit image-visibility item quoted above. There is no "Accessibility," "ScreenCaptureKit," or "Control Center" section anywhere in the document (headings enumerated and checked exhaustively). This is a documented absence, not a gap in my search — the WindowServer/`MenuBarAgent` compositing behavior the prior report reverse-engineered from third-party PRs and issue threads is, as of this research, entirely undocumented by Apple.

**CGWindowList functions carry no discussion or migration text at all.** `CGWindowListCreateImage`'s and `CGWindowListCopyWindowInfo(_:_:)`'s live DocC pages return bare declarations with empty `abstract`/`primaryContentSections` discussion content — no deprecation notice, no "consider ScreenCaptureKit instead" pointer, nothing. This has been true independent of macOS 27 (these are old, effectively unmaintained doc stubs), but it means macOS 27 added no new signal here either. — Sources: https://developer.apple.com/documentation/coregraphics/cgwindowlistcreateimage , https://developer.apple.com/documentation/coregraphics/cgwindowlistcopywindowinfo(_:_:)

## 2. New public APIs that could replace private tricks

**`NSStatusItem.expandedInterfaceDelegate` and `NSStatusItemExpandedInterfaceSession` are new in macOS 27.0** (confirmed via each symbol's own `metadata.platforms[].introducedAt: "27.0"`, fetched directly from the live DocC JSON, not inferred from release-note prose):

- Declaration: `weak var expandedInterfaceDelegate: (any NSStatusItemExpandedInterfaceDelegate)? { get set }` — Source: https://developer.apple.com/documentation/appkit/nsstatusitem/expandedinterfacedelegate
- Discussion (verbatim): *"Status items that assign an `NSMenu` to their button don't receive expanded interface callbacks — the system handles the expanded menu interface automatically. The delegate shows the expanded interface, such as an `NSWindow` positioned beneath the status item, in response to `statusItem(_:didBegin:)`, and dismisses the interface in response to `statusItemDidEndExpandedInterfaceSession(_:animated:)`."*
- The protocol `NSStatusItemExpandedInterfaceDelegate` has exactly two methods: `func statusItem(_ statusItem: NSStatusItem, didBegin expandedInterfaceSession: NSStatusItemExpandedInterfaceSession)` and `func statusItemDidEndExpandedInterfaceSession(_ statusItem: NSStatusItem, animated: Bool)` — Source: https://developer.apple.com/documentation/appkit/nsstatusitemexpandedinterfacedelegate
- `NSStatusItemExpandedInterfaceSession` has exactly one member, `cancel()` — Source: https://developer.apple.com/documentation/appkit/nsstatusitemexpandedinterfacesession
- WWDC26 session 289 gives the intended usage and rationale directly: *"Status items can also be triggers to show custom windows, for example! When a status item shows its window, AppKit needs to know when that UI is active, so that keyboard focus can behave correctly. Track the life cycle of your custom UI, using the expanded interface session API... When it is time to dismiss the session, for example, because an action has been selected, call `.cancel` on the `.expandedInterfaceSession`. Note that the session might be canceled for you, if focus naturally moves somewhere else."* — Source: https://developer.apple.com/videos/play/wwdc2026/289/

**Relevance to Skein:** this API governs how a status item that shows a custom window instead of a menu integrates with keyboard focus. It is directly applicable if Skein's *own* status item (e.g., a hover/click popover for the hidden-items strip) is redesigned to use a custom `NSWindow` instead of `NSMenu`, replacing an ad-hoc first-responder/click-outside-to-dismiss implementation with an AppKit-managed one. It does **not** provide any way to read, move, hide, or attach a delegate to a status item owned by another process — Skein's core "manage other apps' menu bar icons" problem is unaffected.

**`NSMenuItem.preferredImageVisibility` is also new in macOS 27.0** (confirmed `introducedAt: "27.0"` on the live symbol page), letting an app opt individual menu items back into showing their image when the linked-SDK default now hides it. Only relevant to Skein's own menus, not to reading/controlling other apps' menu bar content. — Source: https://developer.apple.com/documentation/appkit/nsmenuitem/preferredimagevisibility

**SwiftUI's `MenuBarExtra` is unchanged in macOS 27** (no `introducedAt: 27.0` marker found on it or on its modifiers); what is new is `NSHostingSceneRepresentation`, which WWDC26 session 272 ("Use SwiftUI with AppKit and UIKit") describes as a way to let an existing AppKit-lifecycle app dynamically insert/remove a complete SwiftUI `Scene`, including a `MenuBarExtra` scene, at runtime: *"I can add a menu bar extra item. SwiftUI's MenuBarExtra scene makes this possible with just a few lines. NSHostingSceneRepresentation wraps a SwiftUI scene and allows it to be added dynamically from an existing AppKit app."* This is a plausible path if Skein ever wants a SwiftUI-authored status item inside its existing AppKit app delegate, but it does not touch third-party status items either. — Source: https://developer.apple.com/videos/play/wwdc2026/272/

**No ControlWidget/Control Center API changes are documented for macOS.** I found zero WWDC26 sessions on Control Center or `ControlWidget` (full 138-session catalog checked by title), and zero mentions in the macOS 27 release notes.

## 3. Privacy/TCC changes

**TCC database direct access is now blocked, per an unqualified line in Deprecations:** *"Apps can no longer access the local TCC database directly."* (90775556) — no further detail, no replacement API named, no severity/timeline qualifier given beyond appearing under macOS 27's "Deprecations" heading. Source: https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes

This matters for Skein/Ice-family apps specifically because reading `~/Library/Application Support/com.apple.TCC/TCC.db` (with Full Disk Access) to silently check Accessibility/Screen Recording grant state — instead of calling `AXIsProcessTrusted()` or `CGPreflightScreenCaptureAccess()` and eating a possible prompt — is a known technique in this app family. Apple's wording ("can no longer access... directly") reads as a hard block, not a soft deprecation warning; treat any existing or planned TCC.db read in Skein as broken on macOS 27 until verified otherwise on-device.

**Cross-developer-team app-data/app-group container access changed from prompt-then-allow to deny-by-default, filed under System Integrity Protection → New Features:** *"Accessing files in other developer teams' app data containers and app group containers no longer prompts the user for authorization; such accesses are denied by default and can be managed by the user in Privacy & Security settings."* (161835690) A second, related item: *"XProtect may now restrict access to app data that is commonly targeted by malicious software. Accessing files created by other developer teams' apps may be denied by default but may be managed by the user in Privacy & Security settings."* (178668601) — Source: same release notes page.

I cross-checked the general Xcode guide "Protecting local app data using containers" (https://developer.apple.com/documentation/xcode/protecting-local-app-data-using-containers) and found it **has not been updated to match**: it still reads *"Any app not in the app group that attempts to access locations protected by an app group or app data container, results in a prompt to the user to authorize access"* — i.e., the old, pre-27 behavior. This is a live inconsistency between Apple's release notes and its general guide; trust the release notes as the more specific/current source, but note the guide itself gives no macOS-27-specific caveat.

**Relevance to Skein:** each Personal-Team (ad-hoc/self-signed) build effectively has its own "developer team" identity distinct from every other app on the Mac, including other builds of Skein signed with a different local certificate if the signing identity ever changes. If Skein ever needs to read another app's container (it does not appear to, based on the task description, but flagging for completeness) or if a companion process of Skein's own needs cross-container access under a different signing identity, macOS 27 makes that silently fail rather than prompt — a behavior change worth testing explicitly rather than assuming prompt-based UX still works.

**A related Known Issue, filed under Privacy & Security Settings:** *"In the Files & Folders pane, a process without a bundle ID cannot be granted access to specific app data containers or app group containers owned by other developer teams."* (184660124) with the stated workaround: *"Consider if the access is necessary. If required, grant Full Disk Access to the process for the duration of the requirement."* Not directly applicable to Skein (a normally bundled app has a bundle ID), but the FDA workaround pattern is consistent with what the prior report found third-party menu bar managers doing for the `MenuBarAgent` preferred-position table.

**No documented change to Accessibility permission, Screen Recording (including any menu-bar capture indicator), Full Disk Access grant flow beyond the above, or security-scoped bookmarks/NSOpenPanel.** I grepped the full release notes for `bookmark`, `NSOpenPanel`, `NSSavePanel`, `App Sandbox`, `entitlement`, `notariz*`, `code sign*`: the only real hits are cosmetic AppKit open/save-panel fixes (new ⌘⇧F shortcut for Recents in open/save panels; Window > Move & Resize/Full Screen Tile now usable on undocked open/save panels; a fix making `allowedContentTypes`/`treatsFilePackagesAsDirectories` correctly drive `canChooseFiles`/`canChooseDirectories` for apps built with the macOS 27 SDK) and one unrelated Accessory Access framework fix for App Sandbox. Nothing touches security-scoped bookmark lifetime, NSOpenPanel's non-sandboxed file-access grant semantics, or Screen Recording.

## 4. Deprecations/removals: CGWindowListCreateImage, CGWindowListCopyWindowInfo, SkyLight/CGS, ScreenCaptureKit

**Neither `CGWindowListCreateImage` nor `CGWindowListCopyWindowInfo(_:_:)` is marked deprecated in the live Apple docs.** Fetched directly from each symbol's DocC JSON metadata:
- `CGWindowListCopyWindowInfo(_:_:)`: `{"beta": false, "deprecated": false, "introducedAt": "10.5", "name": "macOS", "unavailable": false}` — Source: https://developer.apple.com/documentation/coregraphics/cgwindowlistcopywindowinfo(_:_:)
- `CGWindowListCreateImage`: the page carries no `platforms`/availability block at all (an old, essentially unmaintained doc stub with a bare declaration and Mac Catalyst/macOS platform tags on the declaration only, no deprecation flag) — Source: https://developer.apple.com/documentation/coregraphics/cgwindowlistcreateimage

**The macOS 27 release notes make zero mention of either function, of ScreenCaptureKit, or of SkyLight/CGS.** This is consistent across two independent checks (raw-JSON substring count = 0 for `ScreenCaptureKit`, `CGWindowList`, `SkyLight` across the entire ~310-item document, and no relevant subsystem heading). Apple has not signaled any macOS-27-specific tightening of Screen Recording permission requirements, ScreenCaptureKit-only capture, or removal of the older CGWindowList capture path.

**Conclusion for this question:** officially, nothing changed. Any behavioral difference Skein observes around window enumeration or capture on macOS 27 (the prior report documents real, reproducible `CGSGetProcessMenuBarWindowList`/WindowServer compositing changes) is undocumented by Apple and must be treated as unannounced implementation-detail drift, not a supported/flagged API transition.

## 5. "Allow in Menu Bar" / hidden items settings — official user-facing documentation

**An official Apple support guide documents the per-app "Allow in the Menu Bar" toggle**, under "Change Menu Bar settings on Mac":

> *"Allow in the Menu Bar — Some applications provide menu bar items for extra functionality. [Application name] — Select to show in the menu bar."*

and, in the same guide's general options:

> *"Automatically hide and show the menu bar — Choose when to hide and show the menu bar: Always: Always hide and show the menu bar. On Desktop Only: Hide and show the menu bar when not using an app in full screen. In Full Screen Only: Hide and show the menu bar when using an app in full screen. Never: Never hide the menu bar."*

> *"Menu Bar Controls — These items can appear in the menu bar. More items are available in Control Centre."* (lists Clock, Siri, Spotlight, Wi-Fi, Bluetooth, Battery, Focus, Screen Mirroring, Display, Sound, Now Playing, Fast User Switching, Time Machine, VPN, Weather, each with a Show When Active / Always Show choice for several of them)

— Source: https://support.apple.com/guide/mac-help/mchlad96d366/mac (requested with the `/27/mac/27` version path; the server 301-canonicalized to this version-agnostic URL)

**Important caveat — this is not confirmed as macOS-27-specific content.** The page's own version selector, present in the fetched HTML, lists only *"macOS Tahoe 26, macOS Sequoia 15, macOS Sonoma 14, macOS Ventura 13"* — there is no "macOS 27" entry. macOS 27 Golden Gate GA'd 2026-09-14 (confirmed by the official support page "What's new in the updates for macOS 27 Golden Gate," Published Date September 14, 2026: https://support.apple.com/en-us/127257 — a page which itself does not mention the menu bar at all), one day before this research. Requesting the guide with an explicit `/27/` path silently redirected to the same content served for `/26/`, meaning Apple's documentation team has not yet published a distinct macOS-27 edition of the Mac User Guide. The "Allow in the Menu Bar" feature itself is not new to 27 either — independent web sources describe it as a macOS 26 Tahoe feature ("One of the key features in macOS Tahoe is the 'Allow in the Menu Bar' section... You can now selectively enable or disable menu bar icons for any third-party application"). Treat this section's content as "true as of Tahoe 26, presumed carried forward into 27, not independently confirmed by an Apple document that names 27."

**The HIG "The menu bar" page contains general, evergreen (undated) guidance** on menu bar extras that is unchanged prose, not new for macOS 27: *"When necessary, the system hides menu bar extras to make room for app menus. Similarly, if there are too many menu bar extras, the system may hide some to avoid crowding app menus."* and *"Let people — not your app — decide whether to put your menu bar extra in the menu bar... Avoid relying on the presence of menu bar extras. The system hides and shows menu bar extras regularly, and you can't be sure which other menu bar extras people have chosen to display or predict the location of your menu bar extra."* — Source: https://developer.apple.com/design/human-interface-guidelines/the-menu-bar (this page is not reachable via the DocC JSON endpoint that works for the rest of developer.apple.com; I fetched it via a text-extraction proxy after the direct URL and the documented JSON path both failed — flagging per the task's instruction to note unreachable sources).

## What Apple does and does not document — summary table

| Area | Apple documents (official) | Apple is silent on |
|---|---|---|
| NSStatusItem API surface | `expandedInterfaceDelegate`/`NSStatusItemExpandedInterfaceSession` (new 27.0, own status item only) | Any API to read/move/hide another process's status item |
| Menu bar compositing / WindowServer | Nothing | `MenuBarAgent` single-window compositing, `CGSGetProcessMenuBarWindowList`, overflow-chevron layout algorithm, per-display "half width" clamp |
| NSMenu images | `preferredImageVisibility` (new 27.0), default-hide reversal for linked-on-27 apps | — |
| TCC | "Apps can no longer access the local TCC database directly" (Deprecations, no detail) | Any replacement API named |
| Cross-team containers | Deny-by-default, no prompt (SIP New Features) | Interaction with non-sandboxed/Personal-Team signing specifically |
| CGWindowList* | Still `deprecated: false` in live docs | No mention in macOS 27 release notes at all |
| ScreenCaptureKit | No mention anywhere in macOS 27 release notes or WWDC26 catalog | Any macOS-27-specific requirement change |
| "Allow in the Menu Bar" setting | Documented, but only in the still-current Tahoe 26 guide edition | A macOS-27-labeled edition of the same guide does not yet exist |
| Control Center / ControlWidget on macOS | No WWDC26 session, no release-notes section | Everything |

## Unresolved questions

- Whether the "Allow in the Menu Bar" and general Menu Bar settings pane behaves identically on macOS 27 as documented for Tahoe 26 cannot be confirmed from Apple documentation alone, since no macOS-27-labeled edition of the guide exists yet; this needs on-device verification on the build Skein targets (26A428), not another documentation pass.
- Apple's TCC-database deprecation ("Apps can no longer access the local TCC database directly") gives no detail on whether this is enforced by SIP/sandbox at the kernel or file-permission level, whether it applies uniformly to non-sandboxed Personal-Team-signed apps, or what error/behavior results from an attempted read; if Skein or its fork lineage (Ice) reads TCC.db anywhere, that code path needs an on-device test on 26A428, independent of this documentation research.
- Whether the new cross-team container deny-by-default (System Integrity Protection) affects Skein's own app-group or container usage (if any) was not determined here because the task did not point to a specific container Skein reads from another team; if such a dependency exists in the codebase, it should be checked against this change explicitly.
- I could not retrieve the HIG "The menu bar" page through the documented JSON-data endpoint pattern (`/tutorials/data/documentation/design/human-interface-guidelines/...` returned 404); I obtained its text via a third-party read-only proxy (r.jina.ai) instead. The content quoted matches what I could independently verify was live on developer.apple.com via the HTML page's meta tags, but if a stricter definition of "official source" requires the DocC JSON specifically, this citation falls slightly outside that bar and should be spot-checked by loading the page in a real browser.

Summary: Apple's only new, official, menu-bar-relevant public API in macOS 27 is `NSStatusItem.expandedInterfaceDelegate`/`NSStatusItemExpandedInterfaceSession` (scoped to an app's own status item, not third-party ones); TCC direct-database access and cross-team container access both tightened, CGWindowList/ScreenCaptureKit are undocumented and unchanged per live docs, and the "Allow in the Menu Bar" setting is confirmed only for the still-current macOS Tahoe 26 support guide, with no macOS-27 edition published yet.
